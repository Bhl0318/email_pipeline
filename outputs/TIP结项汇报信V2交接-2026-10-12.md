# TIP 结项汇报信 V2 交接说明

> 交给 TIP 系统的会话继续实施。本文以本仓库 `c392805` 及之后的结项 V2 草案为依据；尚未核对 TIP 仓库现状，也未在 atw 真实数据库执行替换 SQL。旧版 [`TIP结项汇报信写入report_tasks交接说明.md`](TIP结项汇报信写入report_tasks交接说明.md) 可用于查看字段背景；涉及地区、规则键和 V2 上线条件时，以本文为准。

## 目标与边界

TIP 的结项表单提交并确认“完成递交”后，用**案号、结项类型一 `cls_task_1`、结项类型二 `cls_task_2`** 查询 atw 的结项规则。根据客户动作：

| `report_rule.action` | TIP 需要做的事 |
| --- | --- |
| `assign` | 若有有效模板正文，创建一条独立的 `report_tasks` 待审核任务；不自动给客户发汇报信 |
| `skip` | 不创建汇报信任务；将规则的 `forward_to` 与 `forward_cc` 合并、去重后加入**原有结项邮件的 CC**，不另转发一封原始邮件 |
| `ignore` / 无匹配规则 | 不创建汇报信任务，也不按本规则增加 CC |

OA 官文流程仍由原始邮件触发，规则域为 `oa`；TIP 结项规则域固定为 `close`。一个案号可有多个 OA 或结项汇报信任务，不使用案号或 `projects.id` 作为 `report_tasks.id`。

## TIP 规则查询顺序

1. **触发条件**：仅 TIP 确认“完成递交”的结项事件进入规则判定。重复提交/重试应关联同一 TIP 事件，不能重复创建汇报信任务。
2. **地区码**：从完整案号固定位置取两位地区码，允许 `CN/CM/CS/US/DS/PR/WO/DM`；本仓库的 [`close_cc.region_of()`](../scripts/report/close_cc.py) 实现了该提取规则。V2 库表使用原码：`CN/CM/CS` 对应 CN sheet，`US/DS/PR` 对应 US sheet，`WO/DM` 对应 PCT sheet。不要把库表地区码统一改成 `PCT` 或 `US`。
3. **匹配项**：先在 `report_rule_map` 中尝试 `match_key = cls_task_1 + '_' + cls_task_2`；如果没有，只有存在 `match_key = cls_task_1` 的“仅类型一”规则时才回退到类型一。两者都没有即未覆盖，不做模糊匹配。
4. **关联键**：从命中行取 `rule_key`，再以 `(rule_domain='close', region, rule_key)` 查 `report_rule` 和 `report_rule_template`。`rule_key` 是规则组的关联值，**不是**需要 TIP 用字符串解析的结项类型。`report_rule_template.template` 再以名称关联 `report_template.name` 读取正文。
5. **客户动作**：客户号取案号前 5 位；先选精确客户号，若该客户号以 `5` 开头再尝试 `5开头`，最后尝试 `其他`。未命中不创建任务、不增加本规则 CC。只有 `status=1` 的规则、映射及模板正文可用于实际任务。

### 短 `rule_key` 与实际匹配键

Excel 一行可列出多个类型二。V2 将其中 17 行的 `rule_key` 简写为 `类型一｜等多项`，例如 CN 的一组规则为 `其他｜等多项`。同一地区、同一类型一存在不同客户动作/模板时，用首项区分另一组，例如 `其他｜等多项（DAS交存）`；不能因为前缀相同就合并两组。其余 44 行沿用 Excel 原规则键。

**TIP 必须查询 `report_rule_map.match_key`，不能从 `rule_key` 文本反推组合。** 比如 `其他_PPH提交` 与同组其他匹配项各占一行 `match_key`，都指向同一个短 `rule_key`；Excel 的完整原匹配键保留在规范化草表的 `source_match_key`，供追溯。

## 模板与结项邮件抄送

- `report_rule_template.template` 保存 **Excel「模板」列原文**，如 `【IDS递交】2026-08-31-IDS递交转达`，并非 `US_IDS递交_V2.md`。TIP 向 `report_tasks.template` 原样写这个名称；审核页通过同名 `report_template.name` 取 Markdown 正文。
- Excel 的 `无需做`：`report_rule_template.template` 为空，不产生汇报信任务；客户若命中 `skip`，只给原有结项邮件增加 CC。Excel 中 CN 的三条特定客户“分配”与此口径冲突，SQL 草案已把这三条转为 `skip`，将原准备人作为 CC 目标。其他客户仍按各自动作 `skip` 或 `ignore` 执行。
- Excel 的 `待填模板（仅表头版）`：需要汇报信任务，正文来源为 `最新版本/模板/待填模板-仅表头版-示例.docx` 转出的草稿；其中原句“关于题述申请，正文事项需要自己编辑”已改成 `{{正文事项}}`，审核页提供多行输入框，发送前要求填写。TIP 可把已知正文写入 `fields_json.正文事项`，否则交给审核人填写。
- 现有 `report_template` 已由业务侧更新。本次只需运行 [`结项V2待填模板正文更新.sql`](结项V2待填模板正文更新.sql)，对同名记录执行 `UPDATE`，把原句换成 `{{正文事项}}`；不重新导入四表规则草案。脚本会显示更新行数及替换前后的占位符位置；更新 0 行时先核对该行是否已修改或正文与原句不同。
- `report_template` 是 OA 与结项共用表，**没有 `rule_domain` 列**。草案只按 Excel 新名称补正文，已有同名不覆盖；不清空该表。旧任务仍可能引用旧 MD 名称。
- V2 草案的 `report_rule_template.attach_pdf` 均为 `0`。递交文件、回执若需随信发出，不能据此认定附件已齐；附件由审核页上传、选择，或以后另做 TIP 文件对接。

## `report_tasks` 写入要求

仅 `action='assign'` 且 `template` 非空、同名 `report_template` 行有效且正文非空时创建：

| 列 | 写入值 |
| --- | --- |
| `id` | 每条汇报信任务独立 UUID；TIP 侧记录 TIP 事件 ID 与该 UUID 的映射，重试复用 |
| `rule_domain` | `'close'`；上线前确认 atw 表已有此列 |
| `template` | 命中的 `report_rule_template.template` 原值，即 Excel 模板名称 |
| `attach_pdf` | 第一阶段写 `0`；与结项文件是否随信附上是两回事 |
| `fields_json` | 至少有 `代理所案号`、`通知类型`（命中的 `rule_key`）、`结项类型一`、`结项类型二`；TIP 已有的案件、客户和完成/递交日期按选中模板的 `{{字段}}` 填入 |
| `report_tasks.close_combination` | 写本次实际命中的 `report_rule_map.match_key`：精确命中为类型一_类型二，回退命中为仅类型一。审核页案号下方及左侧待办列表优先读取该列；为空时显示 `fields_json.通知类型`（`rule_key`）。 |
| `source_attachments` | 无可供汇报信服务读取的本机相对路径时写 `NULL`；不能直接写 TIP 本机路径或 URL |
| `status` | `'pending'` |

`report_tasks` 中没有准备人或 TIP 事件 ID 的专用列；TIP 需自己保存幂等关系，并另行处理准备人通知。创建任务只使 `/review/{id}` 可供审核，不代表已向准备人发链接，也不代表已给客户发信。审核页现有结项专属字段编辑与占位符校验仍需核对。

## TIP 会话接下来的工作

1. 对照 TIP 当前结项提交代码，确认“完成递交”触发点、重复提交幂等、地区码提取、类型一回退顺序。若 TIP 已实现旧规则，不要只替换 SQL 而遗漏查询逻辑。
2. 对照数据库实际结构和已有数据，确认 `report_tasks.rule_domain`、四张规则/模板表及索引；不要仅凭仓库的迁移文件推断生产库已经执行。
3. 在可连接 atw 的受控环境，先校对 CN/US/PCT 模板正文；然后按事务审阅四表替换结果。当前草案末尾是 `ROLLBACK`，并未生效；正式提交须另行审核。
4. 只在规则和模板均准备好后做端到端验证：组合命中、客户优先级、`assign` 只建一条待审核任务、`skip` 只给结项邮件加 CC、`ignore` 不动作、未覆盖类型不动作、重试不重复建任务、审核页按 Excel 模板名显示正确正文。

本说明限定在 TIP 结项触发、规则选择、CC 和汇报信任务写入；不改 OA 官文邮件读取流程。
