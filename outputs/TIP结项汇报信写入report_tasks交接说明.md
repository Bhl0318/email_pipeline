# TIP 结项汇报信写入 `report_tasks` 交接说明

> 结项 V2 已更新地区码、规则键和四表草案；TIP 会话请先阅读 [`TIP结项汇报信V2交接-2026-10-12.md`](TIP结项汇报信V2交接-2026-10-12.md)。本文件保留早期字段背景，冲突处以 V2 交接说明为准。

> 给 TIP 系统开发使用。**第一阶段目标**：TIP 正常结项成功后，按结项规则创建一条待审核的汇报信任务；不改 TIP 既有结项邮件发送流程，也不自动向客户发送汇报信。本文依据本仓库当前规则表读取逻辑、模板和汇报信审核页整理。

## 1. 边界与前置条件

- OA 官文汇报信由原始邮件触发；**结项汇报信由 TIP 结项表单/任务触发**，输入是案号、`cls_task_1`、`cls_task_2` 及 TIP 已确认的结项数据。不需要模拟 OA 官文邮件，也不关联 `projects.id`。
- 在 atw 的 `report_tasks` 表先执行 `scripts/report/add_report_tasks_rule_domain.sql`：增加 `rule_domain VARCHAR(16) NOT NULL DEFAULT 'oa'`。该 SQL **尚未在真实数据库执行**；TIP 上线写入 `close` 前须确认已迁移。
- `report_tasks.id` 继续使用每条汇报信独立的 UUID；**同一案号的多次结项/OA 汇报信是多条任务**，不能用案号当唯一键，也不能把 TIP 结项任务 ID 直接当 `report_tasks.id`。
- 规则、模板映射以 atw 的 `report_rule_map`、`report_rule`、`report_rule_template`（均 `rule_domain='close'`、`status=1`）为准。`report_template` 保存正文，审核页会读它；TIP 不必复制 MD 正文进 `fields_json`。

## 2. TIP 输入与规则判定

TIP 应在“结项成功”这个业务事件上提供以下输入；未完成/未确认的结项不创建汇报信任务。

| 输入 | 用途 |
| --- | --- |
| 代理所案号 `project` | 必需；判法域、客户号、审核页查案件资料及客户收件人 |
| `cls_task_1`、`cls_task_2` | 必需；拼成 **`cls_task_1 + '_' + cls_task_2`**，原值保留，不用邮件主题代替 |
| TIP 结项任务/事件 ID | 必需；重复提交、超时重试时复用同一汇报信任务 ID，避免重复创建 |
| 结项完成/递交日期、申请信息、客户信息 | TIP 能提供的应传入 `fields_json`；按选中模板逐项核对占位符 |
| 递交文件、回执等 | 第一阶段可不入 `source_attachments`；须由审核人上传后才可随汇报信发送 |

按当前结项规则的判定顺序：

1. 从案号识别法域：含 `EP`→EP，含 `US`→US，含 `WO`→PCT，含 `CN`→CN；其他案号直接不创建任务。
2. 在 `report_rule_map` 按 `rule_domain='close' + region + match_key=组合值` 找结项规则键 `rule_key`。**组合不存在即跳过，不做模糊匹配**。
3. 在 `report_rule` 按该 `rule_key` 匹配客户号（案号前 5 位）：精确客户号 → `5开头`（仅客户号以 5 开头）→ `其他`。未命中则不创建任务。
4. 仅 `action='assign'` 且 `report_rule_template` 中存在**非空模板名称**时创建任务；结项 V2 规则使用 Excel「模板」列原文作为名称，须在 `report_template.name` 中有同名有效正文，否则任务虽可写入却无法预览。`skip` / `ignore` / 无模板均不写 `report_tasks`。`skip` 规则的 `forward.to + forward.cc` **不是转发原邮件**，应由 TIP 按既定结项邮件流程合并到抄送名单；此动作与创建汇报信任务互不替代。
   - V2「无需做」行一律不创建汇报信任务；原表中 CN 20615 的 3 个「分配→胡梅」按最新口径转成 `skip`，将胡梅并入结项邮件抄送。
   - 「待填模板（仅表头版）」要创建汇报信任务；`report_template.name` 使用该名称，正文来自 `最新版本/模板/待填模板-仅表头版-示例.docx` 转换并校对后的内容。
   - `outputs/结项V2规则替换草案.sql` 已包含按上述名称补 `report_template` 正文的语句；目前仍是 `ROLLBACK` 校对草案，模板正文须经审核后才能启用。
5. `assign` 规则中的 `preparer` 是汇报信准备人，但现有 `report_tasks` **没有准备人列**。第一阶段只创建任务；入库本身不会自动把 `/review/{id}` 邮件发给准备人，通知需另做对接。

规则表到本仓库规则对象的对应关系可核对 `scripts/report/rules_store.py` 的 `build_close_rules()`；结项抄送语义可核对 `scripts/report/close_cc.py` 的 `resolve_cc()`。

## 3. `report_tasks` 写入契约

| 列 | 第一阶段写入值 | 说明 |
| --- | --- | --- |
| `id` | 新 UUID，重试时复用 | 汇报信任务 ID，也是 `/review/{id}` 的路径参数；不要取 `projects.id` |
| `rule_domain` | **`close`** | OA 任务写 `oa`，结项必须显式写 `close` |
| `template` | 命中的 `report_rule_template.template` | 原样写模板**名称**，例如 Excel 的 `【IDS递交】2026-08-31-IDS递交转达`；不要写 MD 文件名、磁盘路径或正文 |
| `attach_pdf` | 第一阶段建议 **`0`** | 此列控制是否生成/随信附上“汇报信 PDF”；**不能直接映射**结项规则的 `attach_pdf`：结项规则的该值目前表达“递交文件/回执是否随信”，语义不同；审核人可在页面勾选汇报信 PDF |
| `fields_json` | UTF-8 JSON 对象 | 至少包含下节必需键；不得是空字符串、数组或未转义的 JSON 文本 |
| `source_attachments` | 第一阶段建议 `NULL` | 当前审核页只接受相对 `scripts/output/` 的本机文件路径数组；TIP 系统本地路径/URL 不能直接写入。后续文件上传对接或审核人手动上传后再带附件 |
| `status` | `pending` | 审核页发送成功改 `done`，人工跳过改 `skipped` |
| `reviewer` | 不写 / `NULL` | 审核人确认发送时由审核页写入 |

TIP 使用参数化 SQL 写入，列名和值对应如下（示意，**不要直接在生产库运行本示例**）：

```sql
INSERT INTO report_tasks
    (id, rule_domain, template, attach_pdf, fields_json, source_attachments, status)
VALUES
    (?, 'close', ?, 0, ?, NULL, 'pending');
```

如 TIP 程序重试同一个结项事件，应先凭 TIP 侧保存的汇报信 UUID 检查是否已创建；**不要每次重试生成新 UUID 并重复 INSERT**。若 TIP 侧不能保存该 UUID，需先设计稳定的事件 ID 对照/幂等机制，再开放自动写入。

## 4. `fields_json` 字段约定

**必需基础键**（所有结项任务）：

| 键 | 从 TIP 获取/填写 | 审核页用途 |
| --- | --- | --- |
| `代理所案号` | TIP 案号原值，必填 | 查案件资料、客户收件人、发件人默认值、输出目录 |
| `通知类型` | 命中的结项规则键 `rule_key`，必填 | 待办列表显示类型；模板缺“关于”行时作为主题兜底 |
| `结项类型一`、`结项类型二` | TIP 表单原值，建议保留 | 便于追溯组合；现有 OA 审核页**不展示/不编辑**这两个键 |
| `签名品牌` | 根据 TIP 的品牌/发件主体确定；不能确定时留给审核人核对 | 模板落款；发件人邮箱在发送弹窗另行选择，二者需一致 |

**模板用到才必须提供的键**：先选模板，再扫描模板正文所有 `{{字段名}}`；TIP 能取到的必须按同名键放入 JSON，不能凭空填日期，也不能把未完成字段写成看似真实的值。当前结项模板中出现的占位符全集如下：

| 组别 | 模板占位符 |
| --- | --- |
| 案件/客户 | `代理所案号`、`客户名称`、`客户案号`、`申请号`、`申请名称`、`申请日`、`优先权日`、`临时申请到期日` |
| 结项日期 | `完成日期`、`递交日期`、`官文日期` |
| 签名/联系人 | `签名品牌`、`联系人`、`联系人邮箱`、`联系人手机` |
| 特定业务 | `PCT/RO/106 表`、`PCT/RO/132 表`、`专利收费减缴办法` |

例：如果命中 `CN_OA答复递交.md`，模板还要求 `申请号`、`申请名称`、`申请日`、`客户案号`、`客户名称`、`递交日期`、`完成日期`、`联系人`、`联系人邮箱`、`联系人手机` 等。`递交日期` 和 `完成日期` 含义不同，不可互相覆盖。`客户名称`/案件主数据在审核页加载时可能按案号从 atw/IPEasy 补全，但 TIP 已掌握的准确值应优先写入；审核人修改后会更新此 JSON。

仅作**结构示例**（值非真实案件）：

```json
{
  "代理所案号": "12345-0001CN00",
  "通知类型": "OA答复",
  "结项类型一": "OA答复",
  "结项类型二": "第一次答复",
  "客户名称": "示例客户",
  "申请号": "示例申请号",
  "申请名称": "示例申请名称",
  "递交日期": "2026-10-08",
  "完成日期": "2026-10-08",
  "签名品牌": "七星天"
}
```

示例**不是完整可发送数据**：必须按实际模板补齐其余占位符；未补齐时保留 `pending`，由审核人核对，不得自动发给客户。

## 5. TIP 写入后的可见结果与待办

- 插入成功后，现有 `/api/tasks` 待办列表会按 `status='pending'` 查到任务；打开 `http://<汇报信服务地址>:8501/review/{id}` 可读到该任务和 `template`，模板正文由 `report_template`（读不到则同名 MD 文件）提供。**仅 INSERT 不会自动发审核链接、发结项邮件或发客户汇报信**。
- 现有审核页原为 OA 官文设计，`完成日期`、`递交日期`、`官文日期` 等结项专属字段**没有表单输入框**；虽然 JSON 有值时可进入模板预览，但页面上不能直接修改这些字段。待办列表目前取 `发文日期` 显示日期，结项任务不填这个键时日期会留空，不应为了显示而把完成日伪装成官文发文日。全面投入结项审核前，本仓库还需扩展页面字段、显示 `rule_domain`、设置缺失占位符校验及准备人通知。
- 结项规则的 `attach` 要求递交文件/回执时，第一阶段因 `source_attachments=NULL`，**不能视作已经附好文件**。审核人须在页面手动上传并在发送弹窗勾选；TIP 到汇报信服务的附件传递和必传校验需要第二阶段设计。
- `report_tasks` 目前没有 TIP 结项事件 ID、准备人等独立列，第一阶段须由 TIP 侧保存映射与发送状态；如后续要跨系统查询、幂等审计，可另行增加来源事件列，而不是复用 `projects.id`。

## 6. 第一阶段验收清单（仅在有真实库的受控环境执行）

1. `rule_domain` 迁移完成；原 OA 行仍为 `oa`，新结项行写 `close`。
2. 已覆盖组合且规则为 `assign`、有模板的结项，仅产生一条 `pending` 记录；相同 TIP 事件重试不重复。
3. 组合未覆盖、`skip`、`ignore` 或无模板均不创建汇报信任务；`skip` 抄送仍走 TIP 结项邮件。
4. 插入行的 `id`、`template`、`fields_json` 能让 `/review/{id}` 打开正确结项模板；所有必要占位符、附件由审核人核对后再发送。

**本交接只定义 TIP 第一阶段写库，不要求 TIP 修改 OA 官文读取流程，也不代表结项汇报信审核/发信功能已经全部完成。**
